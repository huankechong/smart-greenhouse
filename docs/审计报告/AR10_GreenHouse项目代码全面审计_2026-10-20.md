## 二、问题清单（按严重度排序）

### 🔴 H1 · 连浇上限保护从未生效（固件 waterTick 状态 2）

- **位置**：`outputs/代码/花房代码/GreenHouse_v1/GreenHouse_v1.ino` 修复前 L293-294（状态 2 复测分支）
- **成因**：状态 0 进入首轮时 `waterRounds++`（→1），但状态 2 复测仍缺水转再浇时**没有再次自增**。`waterRounds` 恒等于 1，`if (waterRounds >= MAX_ROUNDS_PER_CYCLE)`（1 ≥ 6）永远为假 → 冷却保护（状态 4）永不可达。
- **影响**：传感器脱土/排线松/探头被土包裹时，状态机在 0→1→2→1→2… 无限循环，每 33 秒放水 3 秒。1L 水箱约 3.6 小时抽干；接大水箱会更久——期间盆会泡烂、泵会空转。v1.2 的两条保护之一实际是空文。
- **证据**（状态机数值模拟，传感器恒判缺水场景）：
  - 修复前：20 个复测周期全部"再浇(未计数)"，浇水 20 次，**从未进冷却**；
  - 修复后：第 6 轮后必进"进冷却"，总浇水 6 次 = `MAX_ROUNDS_PER_CYCLE`。
- **修复**：再浇分支补 `waterRounds++`，日志同步改为 `再浇第 %d/%d 轮`。版本升 **v1.5**。
- **验证**：全关/全开双配置编译 PASS（269,541 B / 902,325 B，RAM 21,592 B / 47,016 B，均健康）；模拟断言全过。

### 🟡 M1 · 水位保护存在 33 秒空窗（固件 waterTick）

- **位置**：修复前状态 1 分支内（原 L269-274）
- **成因**：`gLevelLow` 只在状态 1（浇水中的 3 秒）被检查。**状态 2 停水复测的 30 秒窗口内**水位跌到低点无人管——下一轮若复测通过照浇；**状态 3 远程手动浇水**虽有前置检查，但浇的 5 秒中途水位跌落同样不停泵。
- **影响**：水位临界时，泵可能在几乎无水状态下继续运行数十秒，加速泵体磨损/干烧风险。这是 v1.2 注释宣称"浇到一半也会停泵"的覆盖漏洞。
- **修复（v1.5.1 重构定版）**：水位断泵逻辑提升到 `waterTick()` 顶部——`gLevelReady && gLevelLow && waterState∈{1,2,3}` 时立即 `relayOff()` 并复位状态机。**首版（v1.5）用 `relayIsOn()` 电平门控是错的**：状态 2 进入前继电器必已断开，电平门恒假，状态 2 分支成为死代码（复测期只能"短暂脉冲一拍再停"）。按 `waterState` 判定后三态全覆盖，`relayOff()` 对已断的状态 2 幂等无副作用。
- **验证**：四场景状态机模拟（逐句对齐固件 `return` 语义）：A 水位恒正常→18 浇/3 冷却（上限独立工作）；B 第 2 复测点跌水→恰浇 2 次后在状态 2 被停、此后状态 0 水位门挡住不再浇；C 初始无水→0 浇；D 状态 1 中途跌水→立即复位。全开编译 PASS。

### 🟡 M2 · MQTT 指令大小写敏感（固件 mqttCallback）

- **位置**：修复前 L330
- **成因**：只认小写 `"on"`。巴法云小程序/部分第三方 MQTT 客户端会发 `"ON"`/`"On"`，`msg.trim()` 只去空白不去大小写差异。
- **影响**：答辩现场若用发大写的客户端演示远程浇水，指令被静默忽略——现场排查耗时。
- **修复**：`msg.trim()` 后补 `msg.toLowerCase()` 再比对。行为面唯一变化是接受大写，无副作用。
- **验证**：全开编译 PASS。

### 🟡 M3 · 云端 MQTT 无认证、明文传输（安全，未修·风险可接受）

- **位置**：`GreenHouse_v1.ino` L92-95（`bemfa.com:9501` TCP 明文）、`config.h`（UID 即凭据）
- **成因**：巴法云 9501 端口为 TCP 明文 MQTT，clientID=UID 即"密码"，无 username/password；知道主题名 + UID 即可完全控制设备（订阅指令主题发 on）。UID 还出现在串口日志与 git 历史。
- **影响**：最坏情形 = 陌生人能让水泵浇水 5 秒、看到传感器数据。物理后果轻（3V 驱动小水泵、无锁/门/加热），属**风险可接受的低危**。L1881/TLS 端口巴法云虽提供但 ESP32 2.0.17 的 WiFiClientSecure + PubSubClient 组合在 2MB flash 上偏紧，且课程无此要求。
- **建议**（留档）：① UID 不再进任何截图/日志；② 答辩后到巴法云控制台重置 UID（旧主题数据随之作废）；③ 若日后扩展成真浇花系统，换私有 broker + TLS。

### 🟡 M4 · 局域网 Web 服务无任何鉴权（安全，未修·风险可接受）

- **位置**：`handleRoot()`（EN_WEB 分支）
- **成因**：`WebServer server(80)` 无认证中间件，局域网内任何设备可读数据。本项目**只读无控制端点**（无 `/water` 之类接口），攻击面天然收敛。
- **影响**：同网段者可看湿度/光照数据，无操控面。家庭/课堂 WiFi 场景风险可接受。
- **建议**（留档）：若日后加控制接口，必须先加 `server.authenticate()`；课程演示保持只读即可。

### 🟡 M5 · 依赖锁缺失，跨机编译结果不可复现（依赖，未修·记录在案）

- **位置**：项目无 `libraries.lock` / 版本清单文件；`GreenHouse_v1/README.md` 只写库名
- **成因**：依赖 DHT 1.4.7 / U8g2 2.36.19 / PubSubClient 2.8.0，实验室电脑装库版本若不同（尤其 DHT sensor library 依赖的 Adafruit Unified Sensor 版本漂移）可能编译失败或行为差异。esp32 core 当前 2.0.18-arduino.5，README 验证记录写 2.0.17——**实测 2.0.18 编译亦通过**（本报告编译即为 2.0.18），差异无害但记录口径应统一。
- **修复建议**（下次到实验室执行，5 分钟）：README 库表补版本列；或在实验室 `arduino-cli lib install DHT sensor library@1.4.7 U8g2@2.36.19 PubSubClient@2.8.0` 锁版本。

### 🟢 L1 · `WiFi.localIP()` 假热点风险（安全，未修·场景极窄）

- **位置**：`handleRoot()` 返回 `text/html`
- **成因**：浏览器直接访问 IP 时无 XSS 注入面（数据均为数值），但若日后拼入字符串型传感器数据（如自定义主题名）需转义。
- **建议**：保持"只输出数值"的纪律即可；已留注释价值，不改。

### 🟢 L2 · `readAverage()` 阻塞 50ms（性能，未修·可接受）

- **位置**：`readAverage()` L137-141
- **成因**：10 次 × delay(5ms) = 50ms 阻塞，每 5 秒一次（复测时额外一次）。50ms 内 `mqtt.loop()`/`server.handleClient()` 停摆。
- **影响**：MQTT keepalive 默认 15s、TCP 重传秒级——50ms 抖动无害。实测无丢包风险。
- **建议**：不改。若日后加实时性外设（如蜂鸣器音乐）再改非阻塞状态机。

### 🟢 L3 · HTML 单文件 309KB base64 内嵌（性能，未修·设计目标如此）

- **位置**：`build_html.py` 产物
- **成因**：int16 量化 + base64 全量内嵌，牺牲体积换"离线双击可看"。
- **影响**：加载一次 ~0.3MB，本地打开无感。设计目标（零依赖、可 email 传输）优先。
- **建议**：不改。

### 🟢 L4 · 多脚本 4 段重复的软件光栅化渲染器（风格，未修）

- **位置**：`p0_models.py::render`、`p1p2_models.py::render`、`base_2pc_models.py::render`、`build_assembly.py::render_scene`、`annotate.py` 投影段——同一 z-buffer 三角光栅化实现复制 5 份（各 ~60 行）。
- **影响**：单文件自包含是当时的设计选择（互不 import、单独可跑）；缺陷是光照系数/抗锯齿参数若要调要改 5 处。
- **建议**：答辩材料已冻结，不重构。若 v2 迭代，抽 `outputs/花房3D_common/renderer.py`。

### 🟢 L5 · `check_wires.py` 采样密度对短段不足（风格，未修）
