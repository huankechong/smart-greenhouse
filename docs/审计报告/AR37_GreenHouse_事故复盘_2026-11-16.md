## 二、根因归并：27 → 5

### ◆ A. 二手信息当一手用（7 项，最大根因）

错信了"看似权威但并非实物"的信息源：照片文件名、commit message、分支描述、自己的推断。

- 06a/06b 记反（#20/#21）——信了 R4 照片名和 R3 分支描述
- "闭环已启用"（#18）——把"固件常量就绪"当成"实机在跑"（状态跳级）
- 螺丝归因加戏（#19）——领导没说"买错"，是我补的戏
- README 两次滞后（#4/#26）——实物进度变了没主动核
- PR#24 越权合并（#16）——把"数据核对通过"当成"领导已授权"

**深层机制**：我在信息不完整时有"补全叙事"的倾向——拿到二手信息不去验证源头，而是直接编织成"合理的故事"写进文档。

### ◆ B. 多写者冲突（4 项）

两个 AI 会话同时写一个仓库，互相不知道对方存在。

- reset --hard 冲掉并行会话未提交成果（#7）
- 3D 改动互相回退多轮（#11）
- AR 编号两组重号（#12）
- 行尾噪音挡 pull ×3（#24，本质是 .gitattributes 的 text=auto 与 Python 写文件对同一文件用两把尺子）

**深层机制**：git 保护了"已提交"的内容，但对"工作区未提交"的内容，后到的写者会无声覆盖先到者。

### ◆ C. 中文 Windows 环境三连坑（4 项）

编码（GBK 控制台 vs UTF-8 git 输出）、行尾（CRLF vs LF）、路径（八进制转义显示）。

**深层机制**：每一条都只在中文 Windows 上发生，且都不报错——只是"静默不中/乱码/挡住"，极难第一次就定位。

### ◆ D. 批量脚本无护栏（2 项）

- 误归档 104 个文件（#8）：集合键形态自相矛盾（键不带前缀、查询带前缀），`not in` 恒真
- 空壳残留（#17）：清空目录只跑一轮，不知道要跑到不动点

**深层机制**：批量操作的错误是"一次放大 100 倍"的，但写脚本时的验证习惯还停留在"单次操作"级别。

### ◆ E. 验证不充分就过（4 项，重打成本最高）

- 01b 板槽实心（#5）——建好槽没探针验贯通
- 04 炒面（#6）——打印前没做悬空面审计
- 06c 沉槽/槽口（#22/#23）——嵌槽深度从没实测过
- 接线图 5 轮补丁（#27）——audit 抓不了视觉遮挡，靠目检一轮轮发现

**深层机制**：每类几何/图形有各自的验证盲区，而盲区知识只存在于"踩过坑的人"脑中，没有固化进脚本。

## 三、已沉淀的预防措施

| 根因 | 措施 | 落点 |
|---|---|---|
| A 二手信息 | **一手律**：实物只认领导口述；三态不跳级；PR 无授权不合 | AGENTS §7.5-1 |
| B 多写者 | **单写者律**：重做成本高的目录同时只一会话写；reset --hard 前必 stash | AGENTS §7.5-2 |
| C 编码 | **编码律**：bytes+decode(utf8)+NFC；禁 text=True；CRLF 禁单态 replace | AGENTS §7.5-3 |
| D 脚本护栏 | **护栏律**：dry-run → 白名单断言 → 执行；清目录到不动点 | AGENTS §7.5-4 + 防呆脚本 |
| E 验证不足 | **双验律**：几何必探针、图形必 audit+目检；盲区即时写进脚本 | AGENTS §7.5-5 |

### 自动化：`e_mirror_safe.py` 防呆同步脚本

把根因 C+D 的护栏直接焊进代码（本 AR 同批入库）：
- 中文路径全 bytes + decode(utf-8) + NFC 双侧归一
- 内建白名单断言（先验证 1 个已知文件在镜像集合里，断言失败拒绝执行）
- 只 cp 不 move/delete（破坏性为零，误操作可重跑）
- 完毕自动 md5 复验

## 四、残留风险（无法完全消除的部分）

1. **决策反复**（01b 三轮、04 回退）：这不是 bug——领导看到实物后改主意是正常迭代。预防方式是"打印前给领导看效果图确认"（已在做），但无法根除。
2. **并行会话的存在本身**：只要领导开多个会话，B 类风险就存在。单写者律靠自觉，无技术强制。可能的终极方案：给仓库加 pre-commit 钩子校验"本会话 ID 与锁文件一致"——成本大于收益，暂不做。
3. **中文 Windows 环境**：无法更换 OS，只能靠编码律规避已知坑。
