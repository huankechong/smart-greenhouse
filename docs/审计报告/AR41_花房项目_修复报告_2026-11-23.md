## 一、现象

| 位置 | 现象 |
|---|---|
| App 首页卡片 | 显示 `100% \| 0`，第二位恒为 0 |
| App 设备详情页 | 5 行网格，第一行只有 `100 %` 和 `1012` 两个数值格，**没有字段名** |
| 固件串口 | 光照 raw 稳定在 1001–1038 之间，**完全正常** |
| 巴法云服务器 | 最新 msg 字段齐全，无丢包 |

同一时刻三个观测点对比即可判定：**设备侧无问题，问题在报文格式与 App 解析规则的匹配**。

---

## 二、根因

巴法云 App 的**设备详情页**采用「左格标签 / 右格数值」两两配对的网格渲染：

```
[ 标签A | 数值A ]
[ 标签B | 数值B ]
...
```

它的解析方式是**把 msg 按 `#` 切分后严格两两配对**，第一段当标签、第二段当数值，依次类推。因此：

- 报文开头**不能有前导 `#`** —— 会多出一个空段，把整排配对推歪一格
- 第一段**不能是纯数字** —— 会被塞进「标签」位置，渲染成 `100 %`（数字 + 自动补的百分号），后续所有行随之错位

故障版本共有三种写法，实测对比如下：

| 版本 | 报文 | App 详情页 | App 首页卡片 | 判读 |
|---|---|---|---|---|
| V0（11-19 起长期运行） | `土壤#100#光照lx#1023#温度℃#…` | 第一行无名 | `100% \| 0` | ❌ 光照恒显示 0 |
| V1（19:55 首次修改） | `#100#1023#温度℃#…` | `100 % \| 1023` 无名 | `100% \| 1023` | 数值对，字段名全丢 |
| V2（20:07 二次修改） | `#土壤#100#光照lx#1023#…` | 整体错位 | `0% \| 100` | ❌ 最差，前导 `#` 致偏移 |
| **V3（20:17 定稿）** | `土壤#100#光照#1003#温度℃#…` | **6 行全带标签** | 正常 | ✅ |

V0 之所以「光照恒 0」：按配对规则，`土壤` 未落在标签位，`100` 与 `光照lx` 被配成一对，`光照lx` 转数字失败 → 0。

## 三、修复

### 3.1 固件（`GreenHouse_v1.ino` · `publishData()`）

```cpp
// 修复前
String p = "土壤#" + String(gSoilPct) + "#光照lx#" + String(gLightRaw);

// 修复后（2026-11-23 定稿）
String p = "土壤#" + String(gSoilPct) + "#光照#" + String(gLightRaw);
```

关键约束（已写入函数头注释）：

1. **首字符不能是 `#`**
2. 全程严格 `标签#数值#标签#数值…` 交替，段数为偶数
3. 字段名不带字母后缀（`光照lx` → `光照`），避免和 App 模板冲突
4. 报文字段顺序与小程序面板一致：土壤 / 光照 / 温度 / 气湿 / 状态 / 水位

### 3.2 采集脚本（`outputs/代码/工具/巴法云采集.py`）

本格式变更同时暴露了 AR40 报告里的 **P-6 遗留缺陷**：`parse()` 只按 `|` 切分（旧格式），会把整串吞进 `soil_pct` 且不报错。本次一并修复：

```python
if "|" in msg:                       # 历史格式：字段#值|字段#值
    pairs = [p.split("#", 1) for p in msg.split("|") if "#" in p]
else:                                # 现行格式：标签#值 交替
    seg = msg.split("#")
    pairs = list(zip(seg[0::2], seg[1::2]))
```

键名映射同步补了带单位的写法（`温度℃` / `气湿%`），新旧两种报文均可正确解析。

## 五、连带发现与处置

### 5.1 `config.h` 处于占位符状态导致 MQTT `rc=5`

排查过程中直接编译烧录，MQTT 返回 `rc=5`（未授权）。原因是 `config.h` 于**当日 19:14 被改回占位符**（提交 PR #51 防私钥入库），而板上跑的是此前烧入的真值固件，因此现象延迟暴露。

处置：从 `.workbuddy/backups/2026-11-22_fix/config.h.before_placeholder` 恢复真值。

**遗留风险**：`config.h` 不在 `.gitignore` 中，当前为真值状态。下次提交 PR 前必须手动改回占位符，否则 WiFi 密码与巴法云私钥会进入仓库。

### 5.2 土壤读数持续饱和（非本次 bug）

同期土壤 raw 在 367–720 之间波动，始终低于 `SOIL_RAW_WET = 857`，因此 `safeMap` 钳位输出 100%。原因是盆土湿透且有积水，属**真实读数**，非显示错误。

演示注意：100% 远高于 15% 阈值，自动浇水不会触发。答辩/采访演示前需将传感器插入晾干的土中。

## 六、经验固化

| 结论 | 说明 |
|---|---|
| 巴法云 App 两套 UI，解析规则不同 | 首页卡片取前两段作数值；详情页按 `标签#值` 两两配对。改格式必须在**两个界面**都确认 |
| 排障先取证再改码 | 本次先读串口（设备侧真值）+ 查服务器 API（云端真值），锁定问题在渲染层，避免盲目改传感器代码 |
| 改上报格式必须同步下游 | 任何 msg 格式变更，必须同步 `巴法云采集.py`、小程序面板、文档样例，否则静默产错 |
| 编译前先确认 `config.h` 状态 | 占位符版本编译出的固件能正常启动，但 MQTT 静默失败（`rc=5`），极易误判为网络问题 |
